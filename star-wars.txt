[2026-05-06] — FILE WRITE PROTECTION & THE FALLBACK ENEMY (พี่ช้าง)

Context: stamp_url feature — production server writes uploaded stamp image to local disk.
The question was: "Have you verified the production server CAN write the file to that location?"

The lesson:
  Anything that involves writing to disk (or any I/O) on a production server is a TYPE 2 fact.
  (Type 2 = not necessarily true — OS, permissions, disk space, missing folder are all suspects.)
  You CANNOT assume it will work just because it works in dev.

The enemy — SILENT FALLBACK:
  If your catch block swallows the real error and returns a generic message like
  "อัพโหลดไฟล์ไม่สำเร็จ กรุณาลองอีกครั้ง", the user cannot tell you what went wrong.
  You have no idea if the failure was:
    - Disk full
    - Permission denied on the uploads folder
    - The uploads folder doesn't exist and mkdirSync failed
    - Something else entirely
  This is the fallback acting as your enemy — it hides the problem.

The protection pattern:
  1. Backend: in the catch block, include the REAL error.message in the response.
     Do NOT replace it with a friendly generic message. Return both:
       { error: "Upload failed: " + err.message }
  2. Frontend: ALWAYS display the error to the user. Do not silently swallow it.
     If useUpload() returns error, show it on screen so the user can report back.
     An alert() is acceptable for this case — it stops the process and forces the user to report.
  3. Stop the rest of the process when a write fails. Do not continue as if it succeeded.

Why this matters for debugging:
  If the user sees "อัพโหลดไม่สำเร็จ: EACCES: permission denied, open '/app/uploads/xxx.png'"
  you immediately know EXACTLY what is wrong and where to fix it.
  Compare that to just "อัพโหลดไม่สำเร็จ" — you know nothing.

This is a real-world example of Type 2 fact-finding (from THE DEBUGGING PHILOSOPHY):
  "Different OS, different permissions, different environment" — these are suspects.
  You must EXPOSE them, not hide them behind friendly messages.

[2026-05-05] — THE DEBUGGING PHILOSOPHY (พี่ช้าง — applies to everything, forever)

Step 1: Define the "problem domain"
  Determine the beginning and the end of the reported problem.
  Create the outer scope of knowledge you will need for the current problem.

Step 2: Find the code
  Which files, screens, ts files are related in that problem domain?

Step 3: Read ALL the code first
  Get the full picture of the whole process — before AND after the reported error.
  Do not touch anything yet.

Step 4: Build the "flow picture"
  When you finish reading all of it, you will have a picture of the flow —
  the ordered sequence of what the code is SUPPOSED to do.

Step 5: Classify every fact in that flow into 2 types:
  Type 1 — ALWAYS TRUE: how the language compiler works, how the network
            and server react, protocol behavior. These are universal facts.
            No need to prove them. They are not suspects.
  Type 2 — NOT NECESSARILY TRUE: different OS, different timing, environment
            differences, anything outside of pure technical control.
            THESE are the suspects.

Step 6: Test only the Type 2 suspects
  Log them if necessary. Fix one suspect at a time.

THE CARDINAL RULE (พี่ช้าง's words):
  "Making assumption of 'I think this thing could go wrong' without any
   evidence, proof, or reasonable why to even suspect those things,
   is just a waste of time and energy. It will take you nowhere."

  The real lesson:
    Dev codebase and production codebase can DIVERGE.
    Dev has features in progress, half-pushed files, imports to modules not yet in GitHub.
    Production has only what was intentionally pushed and properly built.
    When you push a server file from dev → always check every import in that file.
    If the imported module is not in the GitHub repo → you MUST push it too (if safe),
    or refactor the import away, before the push will build on production.

  The mechanical difference between dev and production build:
    Dev runs with tsx/ts-node — resolves imports lazily at runtime.
      Missing file → only fails when that code path is actually called.
    Production runs esbuild — resolves ALL static imports at build time.
      Missing file → build fails immediately, nothing runs at all.
    This is why "it works on dev" is not enough. Static imports are a build-time contract.

  The fix applied (dynamic require):
    Let generateWhtCertPdf = async () => { throw new Error("not available"); };
    try { generateWhtCertPdf = require("../pdf-wht-cert").generateWhtCertPdf; } catch {}
    esbuild skips runtime require() in static analysis → build passes.
    If pdf-wht-cert.ts is later pushed to GitHub and pulled → it loads correctly at runtime.

  On the billing-note share bug (redirect to login):
    Root cause: App.tsx (protected) does not have `/share/billing-note/:token` as a
    public route. The React SPA loads index.html → App.tsx auth guard fires → redirect.
    Fix: Express serves a completely standalone HTML page at that route directly,
    bypassing index.html / React / App.tsx entirely. No auth can intercept it.
    This is the correct pattern for any share URL that App.tsx cannot be patched to include.
